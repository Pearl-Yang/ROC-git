## 2.6 详细设计

### 2.6.1 业务流程设计

本节详细描述 ROC-git 课程小组文档协作管理平台的核心业务流程。每个流程都通过流程图+文字说明的形式进行完整描述。

#### 1. 用户登录流程

**流程说明**：用户通过微信小程序进行一键登录，系统自动获取用户身份信息。

```mermaid
flowchart TD
    A[用户打开小程序] --> B{是否首次使用?}
    B -->|是| C[调用 wx.login 获取 code]
    B -->|否| D[读取本地存储的 Token]
    D --> E{Token 是否有效?}
    E -->|有效| F[进入首页]
    E -->|无效| C
    C --> G[调用 wx.getUserProfile 获取用户信息]
    G --> H[将 code + 用户信息发送至服务器]
    H --> I{服务器验证 code}
    I -->|验证失败| J[提示登录失败]
    I -->|验证成功| K[查询/创建用户记录]
    K --> L[生成 JWT Token]
    L --> M[返回 Token + 用户信息]
    M --> N[存储 Token 至本地]
    N --> O[进入首页]
    J --> A
```

**关键节点说明**：

| 步骤 | 操作 | 系统处理 | 异常处理 |
|------|------|----------|----------|
| 1 | 调用 wx.login | 获取临时 code | 网络异常则提示重试 |
| 2 | 调用 wx.getUserProfile | 获取昵称、头像 | 用户拒绝则使用默认头像 |
| 3 | 服务器验证 | 调用微信接口验证 code | 验证失败返回错误码 |
| 4 | 查询/创建用户 | 根据 openid 查询 | 不存在则创建新用户 |
| 5 | 生成 Token | 生成 JWT 包含用户信息 | Token 有效期 7 天 |
| 6 | 本地存储 | 写入 Storage | 存储失败则提示 |

#### 2. 修改个人信息流程

**流程说明**：用户可以查看和编辑个人基本信息（昵称、头像）。

```mermaid
flowchart TD
    A[用户进入个人中心] --> B[获取当前用户信息]
    B --> C[显示个人信息]
    C --> D{用户操作?}
    D -->|查看| E[只读显示]
    D -->|编辑昵称| F[弹出输入框]
    D -->|更换头像| G[调用 wx.chooseAvatar]
    F --> H[输入新昵称]
    H --> I[点击保存]
    G --> J[选择新头像]
    J --> K[上传头像至服务器]
    K --> L{上传成功?}
    L -->|否| M[提示上传失败]
    L -->|是| I
    I --> N[提交修改请求]
    N --> O{服务器验证}
    O -->|验证失败| P[显示错误信息]
    O -->|验证成功| Q[更新数据库]
    Q --> R[返回更新结果]
    R --> S[显示修改成功]
    M --> G
    P --> I
```

**关键节点说明**：

| 步骤 | 操作 | 系统处理 | 异常处理 |
|------|------|----------|----------|
| 1 | 获取当前信息 | 调用 getUserInfo | 接口异常提示 |
| 2 | 编辑昵称 | 限制 1-20 字符 | 超长截断 |
| 3 | 更换头像 | 调用微信 chooseAvatar | 取消则不修改 |
| 4 | 上传头像 | 保存到云存储 | 失败重试机制 |
| 5 | 提交修改 | POST /api/user/profile | 验证失败返回 400 |

#### 3. 创建小组流程

**流程说明**：组长创建小组，并自动生成8位邀请码供组员加入。

```mermaid
flowchart TD
    A[用户点击"创建小组"] --> B[显示创建表单]
    B --> C[输入小组名称]
    C --> D[输入小组描述 可选]
    D --> E[点击"创建"]
    E --> F[前端校验表单]
    F --> G{校验通过?}
    G -->|否| H[显示校验错误]
    G -->|是| I[提交创建请求]
    I --> J[服务器创建小组记录]
    J --> K[生成8位随机邀请码]
    K --> L[将当前用户设为组长]
    L --> M[创建操作日志]
    M --> N[返回小组信息 + 邀请码]
    N --> O[前端显示创建成功]
    O --> P[显示邀请码和小程序码]
    P --> Q{用户操作?}
    Q -->|复制邀请码| R[复制到剪贴板]
    Q -->|分享小程序码| S[调用 wx.showShareMenu]
    Q -->|进入小组| T[跳转到小组主页]
    H --> C
```

**关键节点说明**：

| 步骤 | 操作 | 系统处理 | 异常处理 |
|------|------|----------|----------|
| 1 | 输入小组名称 | 限制 2-20 字符 | 含特殊字符提示 |
| 2 | 生成邀请码 | 8位字母数字组合 | 检查唯一性 |
| 3 | 设置权限 | 当前用户为 leader | 权限持久化 |
| 4 | 操作日志 | 记录创建动作 | 用于审计 |

#### 7. 文件审核流程

**流程说明**：组长审核组员提交的文件，决定通过或驳回。

```mermaid
flowchart TD
    A[组长收到审核通知] --> B[进入审核中心]
    B --> C[获取待审核文件列表]
    C --> D[显示待审核文件]
    D --> E{审核方式?}
    E -->|逐个审核| F[点击单个文件]
    E -->|批量审核| G[多选文件]
    F --> H[查看文件详情]
    H --> I[预览文件内容]
    I --> J{审核决定?}
    J -->|通过| K[点击"通过"]
    J -->|驳回| L[点击"驳回"]
    L --> M[填写驳回原因]
    M --> K
    K --> N{批量?}
    N -->|是| O[遍历选中文件]
    N -->|否| P[提交单个审核]
    O --> P
    P --> Q[服务器验证权限]
    Q --> R{权限足够?}
    R -->|否| S[提示无权限]
    R -->|是| T[更新文件状态]
    T --> U[创建审核日志]
    U --> V[通知组员审核结果]
    V --> W[返回审核结果]
    W --> X[显示审核完成]
    G --> Y[选择多个文件]
    Y --> Z[选择批量操作]
    Z --> AA{批量操作?}
    AA -->|批量通过| K
    AA -->|批量驳回| L
    S --> F
```

**关键节点说明**：

| 步骤 | 操作 | 系统处理 | 异常处理 |
|------|------|----------|----------|
| 1 | 获取待审核 | 查询 status=pending | 权限验证 |
| 2 | 预览文件 | 调用预览API | 格式不支持提示 |
| 3 | 填写驳回原因 | 限制 5-200 字符 | 必填校验 |
| 4 | 批量操作 | 限制≤20个/次 | 超限提示 |
| 5 | 更新状态 | approved/rejected | 事务处理 |
| 6 | 通知组员 | 订阅消息 | 失败日志记录 |

### 2.6.2 接口设计

本节定义 ROC-git 系统的所有 RESTful API 接口。所有接口均已在 `knife4j-spring` 项目中实际实现，可通过 `http://localhost:8080/doc.html` 在线查阅 API 文档。

#### 1. 接口设计规范

##### 1.1 基础规范

| 项目 | 规范 |
|------|------|
| **协议** | HTTPS（开发环境支持 HTTP） |
| **数据格式** | JSON |
| **字符编码** | UTF-8 |
| **接口前缀** | `/api/v1/` |
| **认证方式** | JWT Token（Header: `Authorization: Bearer <token>`） |
| **请求方法** | GET（查询） / POST（创建） / PUT（更新） / DELETE（删除） |
| **响应格式** | 统一 JSON 结构 |
| **文档地址** | `/doc.html`（Knife4j 增强 UI）|

##### 1.2 统一响应格式

**成功响应**：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    // 业务数据
  },
  "timestamp": 1694697600000
}
```

**失败响应**：

```json
{
  "code": 40001,
  "message": "参数错误",
  "data": null,
  "timestamp": 1694697600000,
  "requestId": "abc123"
}
```

##### 1.3 错误码规范

| 错误码 | 含义 | 说明 |
|:------:|------|------|
| 0 | 成功 | - |
| 400 | 请求参数错误 | 参数缺失或格式错误 |
| 401 | 未认证 | Token 无效或过期 |
| 403 | 无权限 | 用户无访问权限 |
| 404 | 资源不存在 | 资源已被删除 |
| 409 | 资源冲突 | 数据重复或冲突 |
| 429 | 请求频繁 | 限流 |
| 500 | 服务器错误 | 系统异常 |
| 10001 | 业务错误码 | 用户相关 |
| 10002 | 业务错误码 | 小组相关 |
| 10003 | 业务错误码 | 项目相关 |
| 10004 | 业务错误码 | 文件相关 |
| 10005 | 业务错误码 | 任务相关 |

##### 1.4 鉴权机制

```mermaid
flowchart LR
    A[小程序发起请求] --> B[携带 JWT Token]
    B --> C[API 网关]
    C --> D{Token 验证}
    D -->|无效| E[返回401]
    D -->|有效| F[解析用户身份]
    F --> G[路由到对应服务]
    G --> H[业务权限校验]
    H --> I{权限足够?}
    I -->|否| J[返回403]
    I -->|是| K[执行业务逻辑]
    K --> L[返回结果]
```
